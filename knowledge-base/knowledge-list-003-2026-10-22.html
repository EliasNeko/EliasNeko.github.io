这一期的关键词：数据。前面十一期学的都是「怎么让它好看」，从今天起是「怎么让它记住」。

02先让数据对，再让它好看

新手做购物车，第一反应是画一个侧边栏，再想办法把东西塞进去。顺序反了。

正确的顺序是：先想清楚数据长什么样，界面只是它的影子。

var cart = [
  { id: "yejia", name: "手冲耶加雪啡", price: 32, qty: 2 },
  { id: "dirty", name: "燕麦dirty",     price: 19, qty: 1 }
]

就一个数组，每格一个对象。用户看到的一切——小计、合计、件数——全都能从这个数组算出来。算不出来，说明数据还不够。

检验标准：如果某个数字只能靠「记住」而不能靠「算出来」，那你的数据结构设计错了。

03事件委托：把监听器挂在爸爸身上

三个按钮，可以各挂一个 click。但如果商品有三十个呢？而且以后还要动态加。

做法是：挂在它们的父元素上，让点击自己「冒泡」上来。

document.querySelector(".cards").addEventListener("click", function (e) {
    if (!e.target.classList.contains("buy")) return;   // 点的不是「加入」就走人
    var name  = e.target.dataset.name;
    var price = Number(e.target.dataset.price);
    console.log(name, price);
});

e.target 是「你真正点到的那个元素」。点击会从它一层层往上冒泡，所以挂在 .cards 上能接住所有子元素的点击。

好处有两个：① 一个监听器管所有按钮，省内存；② 以后新生成的按钮自动生效——购物车里的加减号就是这么做的。

04Number()：不转就会「321」

data-price="32" 读出来永远是字符串，因为 HTML 属性只有文本。

var p = e.target.dataset.price;   // "32"，注意引号
console.log(p + 1);                 // "321"   ← 字符串拼接
console.log(Number(p) + 1);         // 33      ← 这才是加法

更阴险的是："32" * 2 会得到 64。因为乘号没法用在字符串上，JS 悄悄帮你转了。于是「加」错、「乘」对，你查半天查不出来。

规则：从 DOM、URL、输入框、localStorage 里拿到的数字，一律先 Number()。

05对象是引用，不是复制

合并同款时写了这句：

var found = cart[i];        // 不是复制一份，是拿到了那一格的「地址」
found.qty = found.qty + 1;  // 改的是数组里那一格

数组里放对象，放的是门牌号，不是复印件。所以改 found，数组里就真的变了。

反过来，数字和字符串是复制：var a = 5; var b = a; b = 6; 之后 a 还是 5。

一句话：对象和数组是「同一间屋子」，数字和字符串是「抄了一张纸」。

06合并同类项：先找，再决定

点两次同一杯咖啡，不应该出现两行，应该是一行、数量 2。

var found = null;
for (var i = 0; i < cart.length; i++) {
    if (cart[i].name === item.name) {
        found = cart[i];
        break;                 // 找到就停，别傻走到底
    }
}

if (found) found.qty = found.qty + 1;
else cart.push(item);

found = null 是「先假设没有」——一种诚实的写法。break 让循环在找到后立刻停下。

备注：这段手写循环，学了 find() 之后一行就能写完。但先手写一次，你才知道 find() 到底替你做了什么。

07渲染：数据一变，整块重画

不要在每个按钮的回调里各改一处 DOM——改到第五个功能，一定漏。

正确做法：写一个 render()，它只回答一个问题：「现在应该长什么样」。

function render() {
    var count = 0, total = 0, html = "";
    for (var i = 0; i < cart.length; i++) {
        var it = cart[i];
        count = count + it.qty;
        total = total + it.price * it.qty;
        html += '<div class="cart-item">' + it.name + ' × ' + it.qty + '</div>';
    }
    document.getElementById("cartList").innerHTML = html;
    document.getElementById("cartCount").textContent = count;
}

数据变了？调一次 render()。别去追「哪里变了」，只管「现在该是什么样」。

这就是 React、Vue 的核心思想。它们做得更快更聪明，但道理和你这二十行一样。角标显示的是件数（sum of qty），不是种类数（cart.length）——用户关心的是前者。

08innerHTML 的边界

每次循环里都 appendChild，浏览器就要重排一次；三十个商品重排三十次。

更好的做法是先在内存里拼好一整段字符串，最后一次写进页面——只重排一次。

但 innerHTML 有风险：如果拼进去的内容来自用户输入，那就是 XSS 漏洞。

// 危险：用户输入直接拼进 HTML
list.innerHTML = '<p>' + 用户填的内容 + '</p>';

// 安全：先用 textContent 放纯文本
p.textContent = 用户填的内容;
list.appendChild(p);
判断标准不是「用不用 innerHTML」，是「数据从哪来」。自己写死的咖啡名，放心拼；用户填的备注，必须转义。

09localStorage：浏览器给的小仓库

刷新就清空的购物车，没人敢用。

能存什么只能存字符串——这是最要命的限制
存在哪按域名隔离，你的站点一间，别人的摸不到
多大大约 5MB
活多久一直在，除非用户清缓存
localStorage.setItem("coffee-cart-v1", JSON.stringify(cart));
var raw = localStorage.getItem("coffee-cart-v1");
cart = raw ? JSON.parse(raw) : [];
key 为什么要带 v1：以后数据结构变了，换成 v2，旧存档自动作废，不会读到读不懂的数据。

10JSON：出去用 stringify，回来用 parse

JSON.stringify 把对象变成字符串，JSON.parse 把它变回来。

但 parse 遇到坏数据会直接抛错，整个脚本当场死掉，页面变尸体。

try {
    var raw = localStorage.getItem(KEY);
    if (raw) cart = JSON.parse(raw);
} catch (err) {
    cart = [];          // 宁可丢掉存档，也不能让页面崩
}
防御性编程：所有「可能不存在的、可能被改坏的」外部数据，进程序第一件事就是包进 try。坏数据不该让页面死。

11数组的增删：push 和 splice

cart.push(item);      // 末尾加一个
cart.splice(i, 1);     // 从第 i 个开始，删掉 1 个

购物车里「数量减到 0 就删掉这一行」，用的就是 splice。

为什么是减到 0 才删，而不是点减号就删？因为用户的意图是慢慢减。一刀切掉会让人措手不及——交互设计也是产品思维。

12z-index：谁在上面

购物车抽屉做好了，校徽却压在它上面。因为校徽的 z-index 比抽屉大。

10导航栏
95校徽
150购物车遮罩
160购物车抽屉
200口令弹窗
别写 9999。层级要有理由：常驻元素 100 以下，弹层 100–199，压在一切之上的 200 以上。遮罩永远比抽屉低 10——它要衬在后面。

13作用域：函数定义在哪，就只能被哪看见

今天最值钱的一个 bug。

render() 被写进了「点击处理函数」的内部，还忘了调用。结果：数组变了，页面纹丝不动。

// 错：render 定义在点击函数里面
btn.addEventListener("click", function () {
    cart.push(item);
    function render() { ... }   // 外面调不到它
});

// 对：render 放顶层
function render() { ... }
btn.addEventListener("click", function () {
    cart.push(item);
    render();
});
缩进会说话。那段函数缩进了 16 格，比周围的 if 还深——编辑器早就在提示「你放错层级了」，只是没人教过你怎么听。

14设备标签与每日钱包

需求是：每个用户每天 ¥500，刷新不重置。

一开始想用「浏览器指纹」（UA、屏幕、字体拼一个 ID）。最后没用，改用随机生成一个 ID 存起来：

var id = localStorage.getItem("coffee-device-id");
if (!id) {
    id = "u" + Date.now().toString(36) + Math.random().toString(36).slice(2, 7);
    localStorage.setItem("coffee-device-id", id);
}

var today = "2026-10-22";
var w = JSON.parse(localStorage.getItem("coffee-wallet-v1:" + id) || "null");
if (!w || w.date !== today) w = { date: today, balance: 500 };   // 每天重置
为什么不用指纹不稳定（浏览器一更新就变）、隐私敏感、常被防追踪功能搅乱
随机 ID 好在哪只要不清缓存就是同一个，而且只「记住你」，不「认出你」
代价说清楚：换浏览器、清缓存，就变成「新的人」，余额又是 500。这是纯前端的天花板——真要认人，得有后端和登录。

15购买流程：先校验，后扣款

var total = 0;
for (var i = 0; i < cart.length; i++) total += cart[i].price * cart[i].qty;

if (total > wallet.balance) {
    alert("余额不够");
    return;                  // 关键：不动购物车，不扣钱
}

wallet.balance = wallet.balance - total;
saveWallet();
cart = [];
save(); render();

顺序不能反。**先判断能不能买，再扣钱。**反过来写，就会出现「钱扣了但没买成」。

现实提醒：这里的余额是个前端数字，F12 里能改成 9999。真要收钱，价格必须由后端重新计算——前端负责好看，后端负责真金白银。

16今天踩的坑

#踩了什么学到了
1两个 console.log 打同一句话不报错的重复最危险，会把你引向错的排查方向
2render 写进了点击函数里函数定义在哪个大括号里，就只能被那个大括号看见
3git push 退出码 1，其实成功了退出码会撒谎，要看它到底说了什么
4GitHub 直连超时浏览器走代理，git 不走；要给 git 单独配 http.proxy
5校徽压住抽屉z-index 要有层级表，不要临时加数字
备注：五个坑里，两个是「工具在骗你」（退出码、重复日志），两个是「顺序/层级」，只有一个是真的语法问题。写代码的时间，大半花在分辨「谁在骗我」上。
